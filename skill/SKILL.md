# Skill Principle

Agent Skill 的最佳实践原则库，两种用法：**建设**（写新 skill 或迭代已有 skill 时，按原则边建边审）与**审查**（对已有 skill 输出分级问题清单与修改建议）。两条路径共用同一份原则：[references/principles.md](references/principles.md)。

非目标：不代写整份 skill 的骨架或脚手架——建设路径给的是原则指导、结构决策与自审，具体内容仍由用户与当前会话共同写就。（本 skill 版本由 git tag 管理。）

**核心姿态：始终以「将要使用这个 skill 的 Agent」的身份阅读被建或被审的 skill** —— 假装第一次拿到它、要完全依靠它完成任务。凡是这个视角下读不懂、走不通、会误导的，都是问题。

## 路径判定

| 用户意图 | 走哪条 |
|---------|--------|
| 要写一个新 skill；要改进/迭代/重构已有 skill；问「这样写对不对」「该怎么组织」 | 建设路径（Step B1–B5） |
| 要 review / 评审 / 检查质量；要一份反馈报告 | 审查路径（Step R1–R5） |
| 只给了一个 skill 目录、没说要干什么 | 向用户确认是要建设还是审查，不擅自选 |

两条路径不互斥：建设路径的收尾（Step B5）就是对自己产出跑一遍审查路径的判定口径。

## 建设路径

### Step B1：确认意图与边界

- 新建：问清这个 skill 解决什么问题、给谁用、用户会在什么场景下开口、哪些相邻工作**不**归它管。
- 迭代已有：先定位到含 SKILL.md 的根目录，通读 SKILL.md 与全部 references，弄清现有边界与结构再动手；不清楚现状就改，等于制造 2.16 的 patchwork。目标目录及其子目录找不到 SKILL.md → 告知用户该目录不是有效 skill，请其确认路径，不要猜测继续。文件数 > 20 时按 Step R2 的方式先盘点，必要时分块派子代理通读并汇总，避免一次性撑爆上下文。
- 产出：一句话定位 + 非目标清单（对应原则 2.14）。

确认完成后、进入 B2 前，完整阅读 [references/principles.md](references/principles.md) 一次，后续各步只按编号引用，不再重复读取。

### Step B2：写 frontmatter 与 description

按原则 1.1、1.2 落地：`name` 与目录名一致、字段不越白名单；description 三件套齐全——做什么（what）、何时用（when，覆盖用户真实措辞：中英文、口语说法、场景词）、何时不用（排除子句）。写完自查堆砌阈值。

产出：可直接落盘的 frontmatter。

### Step B3：设计结构与披露层次

按原则 2.17、2.5、2.15、2.6 决定文件怎么分：

- SKILL.md 只放触发后必须立刻知道的东西——流程骨架、路由表、判据；执行细节、长模板、枚举清单下沉到 references。
- 每个 reference 在 SKILL.md 中一层直达，且引用处写明读取条件（什么情况才读）。
- 多场景/多模式的 skill 按场景切分入口；预估处理量很大的，先设计分批执行或并行子代理来卸载上下文。

产出：文件清单 + 每个文件的职责与读取条件。

### Step B4：写内容

- 主流程按原则 2.2 写：每步「输入 → 动作 → 产出」，分支点给判据，循环步骤给退出条件。
- 按 2.8 为超过 3 步的流程配 1–2 个案例；按 2.9 为可能失败的场景补「症状 → 原因 → 解法」。
- 正例优先（2.10）；确需写反例时把范围收窄到具体行为（2.11），涉及「绝对禁止」的先问用户。
- 保持 runtime 中立（2.13），不写工程信息与演进史（2.1）。
- 自带 CLI/脚本/第三方依赖/登录流程时，按第三章原则设计安装：独立的 install reference（3.1）、环境隔离（3.2）、状态与凭证分离且凭证入 gitignore（3.3）、失败驱动读取（3.4）、所有运行时资产放在 skill 根目录内（3.5）、跨平台且安装位置可确定（3.6）。

产出：完整的 skill 文件集。

### Step B5：完工自审（强制）

对刚写好或刚改完的 skill，按原则库的「审查」段跑一遍：

1. 先做一次 Step R2 的盘点：列出 skill 根目录全部文件，从 SKILL.md 出发做多跳可达性分析，得到孤立文件集（2.6 的判定输入）。
2. 机械层 1.1–1.4 与通用原则 2.1–2.17 全查；自带 CLI/脚本或安装依赖的，再查 3.1–3.6。
3. **2.12 的「对话约束沉淀」子项在此必查**——建设对话中用户随口提过、但没落进 skill 的约束，是最常见的遗漏。
4. 增量迭代时额外重点核对：2.3 前后文一致、2.16 结构一致性、2.17 披露层次有没有被这次改动改乱。
5. P0/P1 当场修；P2 与「需用户判决」的项（2.6、2.7、2.10、2.11）集中列出，一次性向用户提问，不逐条打断。

产出：修订后的 skill + 一份遗留项清单。用户要一份正式报告时，按 [references/report-template.md](references/report-template.md) 输出。自审收尾后，按 Step R5 询问一次是否启用深度模式。

## 审查路径

### Step R1：确认审查目标

- 用户给出目录或 SKILL.md 路径 → 向上/向内定位到包含 SKILL.md 的 skill 根目录。
- 目标目录及其子目录均找不到 SKILL.md → 告知用户该目录不是有效 skill，请其确认路径，不要猜测继续。
- 未给出目标 → 询问用户要审查哪个 skill。
- 同时确认一个事实供后续使用：**当前对话是否正在建设/迭代这个 skill**（是 → 原则 2.12 的「对话约束沉淀」子项启用；否 → 跳过该子项，2.12 其余检查照常执行）。这一点由自己根据对话历史判断，无需询问用户。

### Step R2：盘点文件与引用图

1. 递归列出 skill 根目录全部文件（排除 `.git/`、`__pycache__/`、`node_modules/`、虚拟环境目录）。若 skill 根目录不是仓库/交付物的顶层（如仓库根下的 `skill/` 子目录），**同时查看其父目录一层**：记录与 skill 根目录平级的 CLI、脚本目录、部署/安装文档（DEPLOY.md 之类）等疑似运行时资产，供原则 3.5 使用。
2. 从 SKILL.md 出发，沿 markdown 链接、路径引用、脚本内部的 import/路径，做**多跳可达性分析**，得到「可达文件集」与「孤立文件集」（供原则 2.6 使用）。
3. **文件数 > 20**：向用户提问是否缩小审查范围。
   - 用户缩小 → 按用户指定范围继续。
   - 用户不缩小 → 按目录/主题拆分为若干分支，**并行派发子代理**，每个子代理负责一个分支；主会话自己保留需要全局视野的原则（2.3 跨文件冲突、2.6 孤立文档、2.4 版本管理、2.16 结构一致性、2.17 渐进披露、3.5 部署内聚性、3.6 跨平台与安装位置），最后汇总。

子代理 prompt 模板：

```
你是 skill 审查子代理。以「使用该 skill 的 Agent」视角审查以下文件：<分支文件列表>
被审 skill 根目录：<路径>
先完整阅读 <本 skill 根目录>/references/principles.md（只用其中每条的「原则」与「审查」两段），
然后对分支内每个文件执行适用的原则判定。
职责边界：2.3 跨文件冲突只标疑点、不下结论；2.4 版本管理、2.6 孤立文档、
2.12 隐式逻辑、2.16 结构一致性、2.17 渐进披露、3.5 部署内聚性、3.6 跨平台与安装位置由主会话统一执行，分支内不要判定；其余 3.x 若判断无安装依赖则标记不适用。
只报告问题，不要修改任何文件。
返回问题列表，每条包含：原则编号、优先级、位置(文件:行)、问题描述、建议修改。
涉及跨文件的疑点（表述冲突、引用缺失）单独标注「需主会话核对」并附上依据。
```

（`<本 skill 根目录>` 即触发本 skill 时系统提供的 base directory。）

### Step R3：按原则库审查

阅读 [references/principles.md](references/principles.md) 并逐条执行其中的「审查」段：

- **机械层（1.1–1.4）与通用原则（2.1–2.17）**：对所有 skill 执行。
- **2.12 的「对话约束沉淀」子项**：仅在建设/迭代该 skill 的对话中启用（见 Step R1 的判断）；2.12 其余检查对所有 skill 执行。
- **依赖与安装原则（3.1–3.6）**：仅当被审 skill 自带 CLI/脚本，或包含需要安装的工具、第三方依赖、登录流程时执行。其中 3.5 部署内聚性与 3.6 跨平台与安装位置还需结合 Step R2 记录的平级资产判断。

执行纪律：

- 每条问题必须落到**位置（文件:行）+ 问题描述 + 建议修改**，不接受"感觉不好"式的模糊反馈。
- 标注「需用户判决」的原则（2.6、2.7、2.10、2.11），发现问题时先**收集暂存**，全部审查完后在 Step R4 统一向用户提问，不要逐条打断。

### Step R4：输出报告并询问判决项

1. 按 [references/report-template.md](references/report-template.md) 的格式输出报告：P0（必须修复）→ P1（应当修复）→ P2（建议考虑），每级内按影响排序。
2. 将暂存的「需用户判决」问题集中列出，逐类向用户提问、由用户决定（孤立文档补引用还是删除、疑似违背机制处是否为环境特例、是否补充"绝对禁止"条目、反例范围是否收窄）。
3. 用户要求修改时才动手修改被审 skill；只要求 review 时，报告即为交付物。

### Step R5：（可选）深度模式

**默认不启用。** 审查完成后（若用户要求了修改，则修改也完成后），询问用户一次，是否启用以下深度模式（可单选或都选）：

- **增强 Review**（联网对照领域现状，评估过时/不一致/遗漏/过度限制）→ 阅读并执行 [references/enhanced-review.md](references/enhanced-review.md)
- **实测验证**（实跑验证：触发率正负样本抽测、行为压力测试、meta 反馈）→ 阅读并执行 [references/behavior-testing.md](references/behavior-testing.md)

建设路径同样可在 Step B5 之后询问是否启用——新写的 skill 最值得做的就是触发率抽测。

## 案例

（案例中的路径均为虚构示例。）

**案例 1 — 建设一个新 skill**：用户说"我想做个 skill，把会议纪要转成任务清单"。B1 问清用途与非目标（只转纪要，不负责建任务到项目管理系统）；读原则库；B2 写出 description：做什么 + 触发语（"会议纪要"、"整理待办"、"meeting notes to todos"）+ 排除子句（不用于日程安排）；B3 判断内容不多，单个 SKILL.md 足够，只把长输出模板下沉到 `references/output-format.md` 并写明"生成最终清单前阅读"；B4 写主流程并补 2 个案例、补"纪要里没有明确责任人"的异常处理；B5 自审发现两处问题：`allowed-tools` 过宽（1.4，P0）、"待办/任务/action item" 三个词混用（2.16，P1），当场改掉，并把 2.10 的禁区候选（是否禁止改写原纪要）提给用户判决。

**案例 2 — 小型 skill 直接审查**：用户说"帮我 review 一下 ~/projects/skills/foo"。确认根目录含 SKILL.md，共 6 个文件，无需拆分。通读后发现：SKILL.md 第 40 行引用 `scripts/convert.py` 但该文件不存在（2.2，P0）；`references/old-api.md` 无任何入链（2.6，P0，暂存待判决）。输出报告后向用户提问：old-api.md 是补引用还是删除。

**案例 3 — 大型 skill 拆分审查**：被审 skill 有 35 个文件。询问用户是否缩小范围，用户选择全量。按 `references/`（18 个文件）、`scripts/`（12 个）、根目录+assets（5 个）拆成 3 个分支并行派发子代理，主会话自己核对跨文件冲突与孤立文档，合并三个分支的结果去重后输出统一报告。
