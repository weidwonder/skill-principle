# Skill 最佳实践原则库

本文件是本 skill 的唯一标准来源，**建设路径与审查路径共用同一份原则**，避免两套标准漂移。

- **建设时**：读每条的「原则」+「建设」两段，作为写作与结构决策的依据；完工自审时再用「审查」段过一遍。
- **审查时**：读每条的「原则」+「审查」两段，逐条判定。每条问题必须给出 **位置（文件:行）+ 问题描述 + 建议修改**，不接受"感觉不好"式的模糊反馈。

本文件较长：需要单条原则时，按编号检索小节标题（如 `grep -n "^### 2.17" principles.md`）直接定位，不必每次通读。

共同姿态：以「将要使用这个 skill 的 Agent」身份阅读；展开见 SKILL.md〈核心姿态〉。

标题中的 `[P0]/[P1]/[P2]` 是**审查时的问题级别**：

| 级别 | 含义 |
|------|------|
| P0 | 会导致使用失败或误导使用者，必须修复 |
| P1 | 明显降低质量或可维护性，应当修复 |
| P2 | 建议考虑，由用户裁量 |

两个标注约定：

- **需用户判决**（2.6、2.7、2.10、2.11）：审查时发现问题先暂存，全部查完后统一向用户提问，不要逐条打断；建设时同样不替用户拍板，列出候选让用户定。
- **主会话执行**（2.3、2.4、2.6、2.12、2.16、2.17、2.18、3.5、3.6）：拆分审查时由主会话统一执行，子代理只提交「需主会话核对」的线索，不在分支内下结论。

## 一、机械层原则（所有 skill 适用；审查时最先做）

### 1.1 [P0] frontmatter 合规

**原则**：frontmatter 是运行时读取的机器契约，字段与取值必须严格合规。

**建设**：只写 `name`、`description` 两个必需字段，按需加 `license`、`allowed-tools`、`metadata`、`compatibility`，其他一律不加；`name` 用小写字母/数字/连字符，与 skill 目录名保持一致；`description` 用第三人称陈述，控制在 1024 字符内、不含尖括号。

**审查**：

- 以 `---` 起止的合法 YAML；字段仅允许：`name`、`description`、`license`、`allowed-tools`、`metadata`、`compatibility`，出现其他字段即报告
- `name`：小写字母/数字/连字符（`[a-z0-9-]`），1–64 字符，与 skill 目录名一致，不含 anthropic/claude 等保留词
- `description`：非空，≤1024 字符，不含尖括号，第三人称陈述

### 1.2 [P0] description 触发质量

**原则**：description 是 skill 唯一的发现/触发机制，必须同时说清「做什么」「何时用」「何时不用」。

**建设**：先写 what（这个 skill 干什么），再穷举 when（用户会怎么开口——中英文、口语说法、场景词、文件类型词，而不是只有技术术语），最后写排除子句（何时不要用、与相邻 skill 的区别）。排除子句不是可选项：它是降误触发的主要手段。写完自检堆砌：引号包裹的触发词串别超过 5 个、逗号分段别超过 8 个——堆砌反而稀释触发信号。「何时用」必须写在 description 里，写进正文无效（正文触发后才加载）。

**审查**：模型倾向于「该触发而不触发」（undertrigger），逐项查——

- 是否同时说清 **做什么**（what）与 **何时用**（when/触发语），并含**排除子句**（何时不要用/与相近 skill 的区别）
- 触发语是否覆盖用户的真实措辞（含中英文、口语说法、文件类型/场景词），而非只有 API/技术术语
- 关键词堆砌：含 ≥5 个引号包裹的触发词串、或 ≥8 个逗号分段 → 报告堆砌警告
- 是否存在与其他常见 skill 高度重叠、可能误触发的表述；审查对象为 **skill 集合**时，扫描同集合内 name 相同或 description 近乎一致的撞车
- "何时用"信息是否误放在正文
- 需要实测触发率时 → 见 `references/behavior-testing.md` §模式一：触发率抽测（经 SKILL.md Step R5 启用）

### 1.3 [P0] Markdown 结构完整性

**原则**：Markdown 语法损坏会让整段内容被 Agent 误读，结构必须完好。

**建设**：写完检查代码栅栏成对闭合——尤其是在文档里嵌套展示 markdown 或 prompt 模板时；表格与链接语法保持可解析。

**审查**：

- 全部代码栅栏（三反引号）是否成对闭合——未闭合会让其后内容全部被当作代码
- 表格、链接语法是否损坏到影响理解

### 1.4 [P0] 安全底线

**原则**：skill 不得携带破坏性操作、凭证或超额权限。

**建设**：涉及删除/覆盖/重置的命令一律配护栏或用户确认步骤；凭证走配置文件而非写进文档或脚本；`allowed-tools` 按最小必要授权，不图省事全开。

**审查**：对所有 skill 执行（不限于有安装依赖的）——

- 脚本与文档中的破坏性命令（`rm -rf`、强制覆盖、`git reset --hard` 等）是否有护栏或用户确认步骤
- 任意文件中是否有硬编码凭证（token、密钥、密码）
- frontmatter `allowed-tools` 是否超出 skill 实际所需（过度授权）

## 二、通用原则（所有 skill 适用）

### 2.1 [P0] 只留使用信息，不留工程信息

**原则**：skill 是给使用它的 Agent 读的运行时指令，不是项目档案。

**建设**：只写「怎么用」，不写「怎么建出来的」。当前规则写清即可，演进史交给 git；面向人类维护者的说明放仓库顶层，不放 skill 根目录内。

**审查**：检查是否存在只与"构建过程"相关、与"使用"无关的内容——

- 开发日志、设计讨论记录、TODO/FIXME 残留、作者自述
- 「以前是 X，现在优化为 Y」式的 old-vs-new 历史叙事——runtime 指令只写当前规则，演进史留给 git
- 构建脚手架残留（init 模板的示例占位文件、示例目录）
- 面向人类维护者而非使用 Agent 的文档（README.md、CHANGELOG.md、INSTALLATION_GUIDE.md、QUICK_REFERENCE.md 之类）
- 测试过程说明、临时实验文件

动作：逐个列出，建议删除或移出 skill 目录。

### 2.2 [P0] 流程与工具完备性

**原则**：主流程的每一步都必须真实可执行、前后衔接、判据明确。

**建设**：每写一步就问自己三件事——这一步引用的脚本/文件/命令存在吗？上一步的产物正好是这一步声明的输入吗？这一步做到什么程度算完成、下一步的分支条件是什么？分支点的判据要写到两个 Agent 读出同一种做法为止；循环/迭代类步骤必须写退出条件。脚本的参数说明以源码为准，不凭记忆写。

**审查**：以使用者身份把 SKILL.md 的主流程从头走一遍——

- 每一步引用的脚本、文件、命令是否真实存在于 skill 内
- 脚本的参数说明与脚本源码实际接受的参数是否一致
- 脚本内部 import / 读取的资源（模板、配置）是否在包内或有获取方式
- 步骤之间输入输出是否衔接（上一步产物是否是下一步声明的输入）
- 是否有断链："见 X 文档"但 X 不存在、"运行上面的命令"但上文没有命令
- **决策点清晰性**：每个分支点是否有明确判据（什么条件走哪条路）？是否存在会让两个 Agent 读出两种做法的歧义表述？
- **完成判据**：关键步骤是否说清"做到什么程度算完成、可进入下一步"（尤其是循环/迭代类步骤的退出条件）

方法：对脚本至少做静态核对（读源码对照文档）；低成本可验证的做 dry-run（如 `--help`）；文档给出了样例输入/预期输出的脚本，用样例实跑并比对实际输出与文档声称是否一致。

动作：输出缺失/断链/不一致清单。

### 2.3 [P0] 前后文表述一致 —— 主会话执行（子代理只标疑点）

**原则**：同一事项在任何位置只有一种说法。

**建设**：参数默认值、步骤顺序、文件路径、命名这类事实只在一处定义，其他位置引用而非复述；改动时全局搜一遍旧值，别只改一处。

**审查**：同一事项在不同位置的表述是否矛盾，**跨文件也要查**——

- 参数默认值、步骤顺序、文件路径、命名、版本号
- SKILL.md 与 references 之间、文档与脚本注释/`--help` 输出之间

动作：列出冲突对（两处位置+两种说法），并建议以哪处为准。

### 2.4 [P1] 版本管理与资产迁移 —— 主会话执行

**原则**：会迭代的 skill 需要版本管理；版本号写在 git tag 里，不写进正文——除非用户资产需要对齐版本。

**建设**：skill 建在 git 仓库内，版本以 git tag 标记。只有当 skill 的更新会影响用户按旧版生成的本地资产（配置、数据文件、模板、目录结构）时，才在 SKILL.md 内标注当前版本并写明版本差异检测与迁移引导；否则正文里不留版本号、更新日志这类 time-sensitive 信息。

**审查**：

- skill 目录是否为 git 仓库（或位于 git 仓库内）？会迭代的 skill 需要版本管理，版本以 **git tag** 标记。
- 若 skill 的更新可能影响**用户资产**，是否有机制提示 Agent 检测版本差异并引导用户做资产迁移/更新，以对齐 skill 版本？**仅在这种场景下**，才需要在 SKILL.md 内标注当前版本供 Agent 对齐；否则避免在 SKILL.md 写版本号等 time-sensitive 信息。

动作：无 git → 建议 `git init` 并打 tag；有资产影响但无迁移机制 → 报 P1 并给出迁移提示的建议写法；无资产影响却在 SKILL.md 内维护版本号/更新日志 → 建议移除、只留 git tag。

### 2.5 [P1] 表述精简

**原则**：能用一个短例子说清的，不写一段抽象描述；同一信息只维护一处。

**建设**：不解释模型本来就懂的常识；SKILL.md 控制在 500 行以内，超了就往 references 拆；单个 reference 控制在 10k tokens 内、references 总量控制在 25k tokens 内，超 100 行的 reference 开头给目录。发现自己在同一个 skill 里混用多种语言的代码块、或想覆盖一堆不相干场景，说明该拆成多个 skill 了。

**审查**：

- 同一信息是否在 SKILL.md 与 references 中重复维护（该留哪一处由 2.18 判归属）
- 是否有大段解释模型本来就知道的常识
- 是否有可用 1 个简短例子替代的长段抽象描述
- SKILL.md 是否超过 500 行（应拆分到 references）
- 分级 token 阈值：单个 reference >10k tokens 警告、>25k 报问题；references 总量 >25k 警告、>50k 报问题（超标 → 拆分或提供 grep 检索模式）；超过 100 行的 reference 是否在开头提供目录（TOC）
- 范围聚焦度：同一 skill 的代码块混用多种语言、或试图覆盖过多不相干接口/场景，是应拆分为多个 skill 的信号

动作：指出可精简的段落，给出建议措辞或拆分方案。

### 2.6 [P0] 无孤立文档/工具 —— 需用户判决；主会话执行

**原则**：skill 内的每个文件都要能从 SKILL.md 一层直达；到不了的等于不存在。

**建设**：每新增一个 reference 或脚本，立刻在 SKILL.md 里补上引用与读取条件。避免深层嵌套引用（reference 再引 reference 才能到达）。删内容时同步删引用，别留断链。

**审查**：从 SKILL.md 出发做多跳可达性分析：沿 markdown 链接、正文中的路径引用、脚本内部 import/路径，标记所有**经多跳仍不可达**的文档、脚本、资产。注意：

- 一整组互相引用但整组都没有来自 SKILL.md 链路入口的文件（孤立文档集），同样算孤立。
- 可达 ≠ 一层可达：reference 文档应从 SKILL.md **一层直达**。可达但需多跳的 reference，报 P1 并建议在 SKILL.md 中补直接引用。

动作：列出孤立文件清单 → 统一向用户提问：补充引用，还是删除。

### 2.7 [P0] 不违背常识/机制 —— 需用户判决

**原则**：指令不能要求 Agent 做平台机制之外的事，也不能写错事实。

**建设**：写之前确认平台真的支持——常驻监听、跨会话记忆、非标准 frontmatter 字段这类能力多半不存在；API 用法、命令语法、格式规范以官方文档为准，不凭记忆写；流程顺序检查一遍因果（先装后用、先读后生成）。

**审查**：

- 指令是否与平台机制冲突：要求 Agent 做其能力之外的事（常驻监听、跨会话记忆、读取不存在的 frontmatter 字段）、假设工具具有实际没有的能力
- 是否有事实性/技术性错误（API 用法、命令语法、格式规范）
- 流程逻辑是否自洽（先用后装、先读后生成之类的顺序颠倒）

动作：列出 → 询问用户判决（可能是用户环境特有的机制，不可武断判错）。

### 2.8 [P1] 案例覆盖

**原则**：案例是最优的说明方式，优于加长抽象描述。

**建设**：超过 3 个步骤的流程、含 ≥3 个必须按序完成动作的过程、引入 ≥2 个新概念的方法，各配 1–2 个案例，用最简洁的语言讲清**过程和结果**（输入 → 关键动作 → 产出）。案例用虚构但合理的路径与数据，别塞真实工程细节（见 2.1）。

**审查**：对以下对象检查是否配有案例——

- 超过 3 个步骤的流程
- 单个过程含 ≥3 个必须按序完成的动作，或引入 ≥2 个新概念/实体的方法

标准：每个场景至少 1–2 个案例，讲清过程和结果。

动作：指出缺案例的流程，并给出建议的案例骨架。

### 2.9 [P1] 异常场景说明

**原则**：报错信息不足以让使用 Agent 自行脱困时，skill 要补上「症状 → 原因 → 解法」。

**建设**：列一遍主流程可能失败的场景（网络不通、鉴权失效、文件缺失、格式不符、依赖版本漂移……），逐个判断环境或脚本给出的报错够不够用；不够用的，要么改进脚本报错，要么在 skill 里补症状-原因-解法。

**审查**：枚举主流程可能失败的场景，逐个判断——

- 该场景下环境/脚本反馈的报错信息，是否足以让使用 Agent 自行定位原因并解决？
- 不足以 → SKILL 中是否补充了「症状 → 原因 → 解法」的说明？

动作：列出报错语义不足且 SKILL 未覆盖的异常场景，建议补充说明或改进脚本报错。

### 2.10 [P2] 正例优先与关键禁区 —— 需用户判决

**原则**：正例优先。反例会让模型回避「与反例相关但实际可行」的行为，只用来守绝对禁区。

**建设**：默认用正面表述写「该怎么做」。只有确认存在「绝对不可以」的操作（不可逆、危及安全、违反合规）时才写反例，且必须先与用户确认，不自行判定禁区。

**审查**：若整个 skill 中没有任何反例，对其中的**重要过程**收集候选风险点 → 询问用户：是否存在"绝对不可以"、"绝对不能"的操作需要写入 skill。

动作：询问用户，用户确认后才补充。

### 2.11 [P1] 反例范围准确 —— 需用户判决

**原则**：每条反例的范围必须刚好覆盖真正要禁的事，不多禁一分。

**建设**：写反例时把范围收到具体行为上（"未经确认上传用户数据"，而不是"禁止使用网络"），并顺手想一遍：这条会不会误伤某个正常做法？会就再收窄。

**审查**：对已有的每一条反例逐条评估——

- 表述范围是否过宽？（例：写"禁止使用网络"，实际只想禁"未经确认上传用户数据"）
- 是否会误伤正常、可行的行为？

动作：列出疑似过宽的反例及其可能误伤的场景 → 与用户确认收窄后的准确范围。

### 2.12 [P1] 隐式逻辑显式化 —— 主会话执行

**原则**：使用时必须知道的关联，不能只存在于作者脑子里。

**建设**：写完后枚举 skill 涉及的实体（工具、文件、状态、配置、角色），逐对检查有没有没写出来的依赖——脚本 A 的输出目录必须与配置 B 的路径一致、状态文件 C 由步骤 2 创建而步骤 5 依赖它。**建设对话中尤其要回头翻一遍对话**：用户随口提过的约束常常没落进 skill，因为注意力都在显式诉求上。

**审查**：枚举 SKILL 中说明的实体，检查（**对所有 skill 执行**）——

- 实体之间是否存在文中未写明、但使用时必须知道的隐式关联

附加子项——**对话约束沉淀**（仅当当前对话本身就在建设/迭代这个 skill 时启用）：

- 对话上下文中用户透露过、但没有落进 skill 的约束

动作：建议补充进 skill。

### 2.13 [P1] Runtime 中立性

**原则**：除非明确声明只服务某个宿主环境，正文不绑定具名工具/命令。

**建设**：写「向用户提问」而不是点名某个提问工具；写「用检索工具查找」而不是写死某个命令。确实要绑定时，明确声明适用环境，并给出通用降级表述。

**审查**：

- 正文是否绑定特定宿主环境的具名工具/命令（除非 skill 有意只服务该环境并明确声明）
- 绑定处是否有通用降级表述（如"向用户提问"而非点名某个提问工具）

### 2.14 [P1] 目标与非目标清晰

**原则**：正文要说清 skill 干什么，更要说清它不干什么。

**建设**：开头一段写定位与工作范围，紧跟一句非目标（哪些相邻工作不由它负责、该找谁）。与 1.2 分工：description 管触发边界，正文管职责边界。

**审查**：

- 正文是否说清 skill 的工作（做什么）与边界（不做什么/非目标）
- 与 1.2 的分工：1.2 管 description 的触发质量，本条管正文的职责边界——缺非目标声明的 skill 容易被拿去做不该做的事

### 2.15 [P1] 读取条件边界

**原则**：每个 reference 的引用处都要写明「什么条件下才读」。

**建设**：引用 reference 时把条件写在引用旁边（"仅当…时阅读"）。没有条件的 reference 要么每次都被读（浪费上下文），要么永远不被读（形同孤立）。

**审查**：

- SKILL.md 引用每个 reference 处，是否写明「什么条件下才读」
- 缺读取条件的 reference 容易被每次都读或永远不读；3.4 是本条在安装文档上的特例

### 2.16 [P1] 结构一致性 —— 主会话执行

**原则**：一个概念一个名字，一件事一处权威表述，编号与层级前后统一。

**建设**：迭代时优先改写既有段落，而不是在旁边新增一段近似表述；新增小节沿用既有的编号与组织方式；换用词前先全局替换旧词。被多个 LLM/Agent 来回修改过的 skill 尤其要做这一遍。

**审查**：针对 patchwork 症状，**跨文件也要查**。与相邻项分工：2.3 管"同一事项两种说法互相矛盾"，2.5 管"同一信息重复维护"，2.18 管"这条事实该住在哪"，本条管介于其间的混乱——

- **术语漂移**：同一概念/实体在不同位置使用不同名称
- **近似重复**：表述略异、语义几乎相同的段落并存，无法判断哪个是权威版本
- **结构断裂**：编号/层级/风格在文档中途断裂或混杂（步骤编号跳号或重号、同一文档混用多套小节组织方式、列表风格无理由切换）

动作：列出漂移术语对与近似重复段落对，建议统一为单一术语/单一权威表述；结构断裂处给出统一的组织方案。

### 2.17 [P1] 渐进披露与注意力控制 —— 主会话执行

**原则**：判断标准是**「Agent 在任一时刻要同时持有多少信息」**，而不是信息总量。

**建设**：SKILL.md 只放触发后必须立刻知道的东西——流程骨架、路由表、判据；执行细节、长模板、枚举清单、大表格下沉到 references，在引用处写清读取条件。多场景的 skill 按场景切分入口，让 Agent 只加载当前场景那一份。长流程拆成有序、可单步执行的步骤，每步一个目标、有输入→动作→产出，需要跨阶段保持的状态落到文件/清单里而不是全靠上下文记着。单步并列硬性约束别超过 7 条、别同时要求读 3 个以上 reference、单个小节别一次引入 5 个以上新概念。处理量可能很大时（批量文件、大范围扫描），设计分批执行或并行子代理来隔离上下文。

**审查**：与相邻项分工：2.5 管信息是否冗余/超体积，2.6 管引用是否可达、层级是否过深，2.15 管每个 reference 引用处**有没有**写读取条件，本条管**投放节奏与单点负荷**——

- **分层管理**：SKILL.md 是否只承载「触发后必须立刻知道的东西」；若 SKILL.md 中有大段只在某个特定分支才用得到的细节（走其他分支的执行都要白读一遍）→ 报问题
- **场景分割**：多场景/多模式的 skill，是否按场景切分入口；把所有模式的指令混在一个文件里、靠 Agent 自己筛选适用条目 → 报问题
- **任务拆解**：长流程是否拆成有序、可单步执行的步骤，每步有清楚的输入 → 动作 → 产出。与 2.2 的分工：2.2 查判据「有没有」，本条查颗粒度——单个步骤是否塞进了多个不相干目标
- **逐步执行**：流程是否被写成「一次性抛出全部信息、由 Agent 自行编排」，而非按阶段推进。需要跨阶段保持的状态是否有落点（文件/清单）
- **单点注意力负荷**（经验阈值，超出即提示拆分或分阶段披露，非硬性判错）：单个步骤内并列硬性约束 > 7 条；单个步骤同时要求读取 ≥3 个 reference；单个小节同时引入 ≥5 个新概念/实体
- **披露时机错配**：只在特定条件下才需要的内容（异常处理、安装登录、深度模式、边缘场景）是否被放在主路径上；反向错配同样报——主路径必需的关键约束被藏进条件性 reference
- **上下文卸载**：处理量可能很大时，是否设计了分批执行或并行子代理来隔离上下文；无任何卸载机制且体量确实会撑爆上下文 → 报问题

动作：给出分层重构建议——具体哪些段落下沉到哪个 reference、SKILL.md 保留哪些骨架与路由、路由的读取条件怎么写；步骤颗粒度过粗的给出拆分后的步骤序列。

### 2.18 [P1] 事实归属单一 —— 主会话执行

**原则**：一个事实只有一个家，别处只写「名字 + 指针」。家可以是本 skill 内的某个文件或小节，也可以是相邻的另一个 skill；家以外的位置可以就地重复读者在那里非知道不可的关键一句，但展开、例子、例外只写在家里。

**建设**：写任何规则、阈值、清单之前先定它的家——先照 2.14 的非目标判这件事归不归本 skill 管：不归 → 点名那个 skill（skill 名 + 文件名 + 小节名）并给一句"什么时候去读它"，不复述它的判据；归 → 定到具体文件与小节，并在 SKILL.md 的路由/归属表里登记一行。skill 划分得好的标志，就是跨 skill 之间只剩指针：同一条规则在两个 skill 各展开一遍，两边会各自迭代，必然写岔，而使用它们的 Agent 无从判断信哪份。指针要写得能直接跳到，不写"详见相关文档"。

**审查**：跨文件、跨 skill 都要查。与相邻项分工：2.5 管同一信息重复维护带来的体积浪费，2.16 管近似重复段落并存导致的措辞漂移，2.3 管两处已经写矛盾，本条管**归属**——谁是这条事实的家、别处该不该展开。

- **多家并存**：同一条规则/阈值/清单在两个文件或两个 skill 各展开一遍（即便当前措辞一致）→ 报问题，指明应当留下的那个家
- **越界展开**：2.14 的非目标里已划给别人的事，正文却写了完整判据或流程 → 报问题，改为点名 + 指针
- **有家不指**：正文重新解释一件别处已有权威表述的事，却没有指针指过去
- **有指针没有家**：指针指向不存在的文件/小节，或几处互相指、谁都没有展开 → 按流程断链报 P0（同 2.2）
- **归属表缺失**：skill 含 ≥3 个 reference，或与同体系的其他 skill 有明确分工时，SKILL.md 是否有一张路由/归属表说明「哪类事实住在哪」

动作：逐条给出归属判定——每条多家并存的事实指定唯一的家，其余位置改写成「名字 + 指针」的一行；缺归属表的给出表格草稿。

## 三、依赖与安装原则（仅当 skill 自带 CLI/脚本，或含需安装的工具/第三方依赖/登录时适用）

### 3.1 [P0] 独立安装指导

**原则**：安装说明独立成篇，复杂安装配脚本。

**建设**：把安装步骤集中写进一个 reference（如 `references/install.md`），不要散落在主流程里。多步骤、多依赖、需编译的工具集，附一个安装脚本。

**审查**：

- 是否有独立的安装指导说明（单独的 reference 文件，而非散落在正文）？
- 工具集安装较复杂（多步骤、多依赖、需编译）时，是否附带安装脚本？

### 3.2 [P0] 环境隔离

**原则**：安装尽可能不影响系统环境。

**建设**：Python 用 venv / uv 建独立环境，Node.js 用项目局部 `node_modules`，不做系统级配置修改。确实无法隔离时，显式警告并说明影响。

**审查**：

- Python → venv / uv 等独立依赖环境，禁止直接 pip install 到系统环境
- Node.js → 项目局部 node_modules，避免 `npm install -g`
- 不修改系统级配置；确实无法隔离时，是否显式警告并说明影响

### 3.3 [P0] 状态/凭证 JSON 分离

**原则**：安装状态可入库，凭证绝不入库。

**建设**：用两个 json 文件分别记录「依赖环境是否装好」与「登录凭证」；凭证文件写进 `.gitignore`；CLI/脚本默认从凭证 json 读凭证；SKILL.md 声明默认前提——每次使用时默认工具已装、用户已登录，直接进入使用流程。

**审查**：

- skill 目录下是否约定了 **json 文件**记录：依赖环境是否已装好、登录凭证。且状态与凭证必须**分离为两个文件**：安装状态 json 可随 skill 提交；**凭证 json 必须列入 `.gitignore`、禁止随 skill 提交**（对照 2.4 的 git 化要求——凭证入库是要拦下的事故）
- CLI/脚本是否默认从凭证 json 读取凭证
- SKILL.md 是否声明默认前提：**每次使用 skill 时，默认所有工具已安装、用户已登录**，直接进入使用流程

检查时同时核实：凭证文件路径是否真的被 `.gitignore` 覆盖、有没有已被提交的凭证痕迹。

### 3.4 [P1] 失败驱动安装

**原则**：安装是异常路径，不是主路径第一步。

**建设**：把安装说明的读取条件写成「仅当工具报错或鉴权失败时才阅读」，主流程直接假定已装好。

**审查**：

- 只有当工具调用报错、或返回鉴权失败时，才回头执行安装/登录流程
- SKILL.md 引用安装说明文档处，是否把这一点写成**读取条件**，而不是每次都读、或把安装放在流程第一步

### 3.5 [P0] 部署内聚性（高内聚、低耦合）—— 主会话执行

**原则**：skill 以「含 SKILL.md 的根目录」为单位分发和安装，运行时所需的一切必须随该目录走。

**建设**：自带的 CLI、脚本、工具放进 skill 根目录内的子目录（`scripts/`、`cli/`），安装部署说明放进 `references/`；所有引用路径都落在 skill 根目录内，出现 `../` 越界就是耦合信号。仓库顶层的 README、CHANGELOG、dist 产物面向人类维护者，不属于交付物，不受此条约束。

**审查**：逐项检查——

- skill 自带的 CLI、脚本、工具是否放在 skill 根目录**内部**？与 skill 根目录**平级**放置（如仓库根下 `skill/` 与 `cli/` 并列）→ 报 P0：安装 skill 时这些工具不会随之分发，装好即断链
- 安装/部署说明（DEPLOY.md、INSTALL.md 之类）是否作为 skill 内的 reference 存在？放在 skill 根目录之外 → 使用 Agent 触发 skill 后根本不可达，等同不存在（本条是 2.6 可达性在部署文档上的特例）
- SKILL.md 及 references 中引用工具/脚本的路径是否都落在 skill 根目录内？出现 `../` 越界引用即为耦合信号

动作：列出所有位于 skill 根目录之外、但运行时必需的文件（含盘点父目录时记录的疑似资产）→ 建议移入 skill 根目录内的相应子目录，并修正全部引用路径。

### 3.6 [P0] 跨平台与安装位置 —— 主会话执行

**原则**：安装方案要尽可能跨平台、位置可确定，并优先与 skill 一同分发。

**建设**：明确声明支持的操作系统与架构，为每个受支持平台给出可执行的安装步骤，优先选跨平台运行时或包管理器；天然只支持部分平台的工具，写清不支持的平台与替代路径。可携带的依赖装进 skill 根目录内的专属子目录（`tools/`、`.venv/`、`node_modules/`），路径由 skill 根目录相对推导，不写死用户目录、不依赖未说明的全局 PATH。装不进 skill 目录的（操作系统包、受管运行时），说明原因、各平台实际位置、对系统的影响与恢复方式。安装脚本按平台选对下载物与路径分隔符，遇到不支持的平台明确失败而非静默装错。

**审查**：涉及软件安装、CLI 或其他程序性依赖时——

- 是否明确支持的操作系统与架构，并为每个受支持平台提供可执行的安装步骤？若工具天然仅支持部分平台，是否明确声明不支持的平台及可行替代路径？
- 每个平台下是否明确依赖的最终安装位置，以及运行时如何从该位置发现可执行文件或环境？禁止依赖未说明的全局 PATH、当前工作目录或用户主目录的默认位置。
- 可由 skill 自行安装的依赖，是否优先安装到 skill 安装目录内的专属子目录，而非系统级、用户级或全局目录？安装目录必须由 skill 根目录相对路径推导，禁止写死特定用户目录。
- 确实无法安装在 skill 目录内时，是否说明原因、各平台实际位置、对系统的影响与恢复方式？
- 安装脚本是否根据当前平台选择正确的下载物、文件扩展名与路径分隔符，并在不支持的平台上明确失败？

动作：报告缺失的平台覆盖、不可确定的安装位置、全局安装或硬编码用户路径；建议将可携带依赖迁入 skill 根目录内的专属子目录，并为各受支持平台补齐位置与发现机制。
